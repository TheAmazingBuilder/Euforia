Section 1
Vue d'ensemble & architecture

Oryon (nom de code interne Cosmoz) est une plateforme de trading analytics en monorepo pnpm + Turborepo. Un frontend Next.js, une API NestJS et des micro-services optionnels coopèrent autour d'un contrat de données partagé (packages/shared, schemas Zod) : types, primitives monétaires (decimal-string, UTC strict) et utilitaires de sécurité (assainissement CSV).

ComposantStackPort devDossier
Web (frontend)Next.js App Router + Tailwind + Radix + TanStack Query v53000apps/web
API (backend)NestJS + Prisma + class-validator4000apps/api
Base de donnéesPostgreSQL 17 embarquée (dev)5433apps/api/.localpg
OCR service (optionnel)FastAPI (Python)3004mini-services/ocr-service
Market service (optionnel)Bun sidecar3003mini-services/market-service

Flux en mode réel : le navigateur parle au web (:3000) ; les appels API partent vers le même origine sous /api/v1 et sont proxifiés vers l'API (:4000). Aucun CORS à gérer en local, cookie de refresh first-party. Le backend MSW simulé est désactivé dans la configuration livrée — vous tapez toujours sur la vraie API et votre vraie base.

Base vide par design
Aucun seed, aucun jeu de données fictif, aucun compte de démo n'existe dans le dépôt. Après migration du schéma, toutes les tables sont vides : vous remplissez la base avec vos propres données via l'interface (Section 8).

Section 4
Installation des dépendances
pnpm install --frozen-lockfile

Une seule commande installe tout : web, api, packages/shared, et génère le client Prisma (postinstall). Comptez 1 à 3 minutes sur une machine neuve. Ne retirez --frozen-lockfile que si vous ajoutez volontairement des dépendances.

5.2 Web — apps/web/.env.local
NEXT_PUBLIC_API_MOCKED=false API_PROXY_TARGET=http://localhost:4000
⚠ NE PAS omettre NEXT_PUBLIC_API_MOCKED=false
Sans cette ligne, le mode dev Next.js reste sur le backend MSW simulé (données fictives). Avec false, toutes les requêtes partent sur votre vraie API via le proxy same-origin — zéro mock. En build production, le mode réel est imposé.
Section 6
Base de données — vide par design
Option A — PostgreSQL embarquée (recommandée en local)
pnpm api:db:up # démarre PostgreSQL 17 sur 127.0.0.1:5433 pnpm --filter @cosmoz/api db:status # vérifie l'état pnpm --filter @cosmoz/api exec prisma migrate deploy # applique les 42 migrations

Binaire géré par la dépendance embedded-postgres — aucune installation système. Authentification trust sur 127.0.0.1 uniquement (convenience dev). Les données vivent dans apps/api/.localpg/ (créé au premier db:up, hors git). db:down stoppe, db:status diagnostique.

Option B — Votre propre PostgreSQL (Docker)
docker run -d --name oryon-pg -e POSTGRES_USER=oryon \ -e POSTGRES_PASSWORD=change-me -e POSTGRES_DB=cosmoz \ -p 5433:5432 postgres:17 # puis adaptez DATABASE_URL dans apps/api/.env : # postgresql://oryon:change-me@127.0.0.1:5433/cosmoz pnpm --filter @cosmoz/api exec prisma migrate deploy

Pourquoi la base sera vide — et c'est voulu : aucun fichier de seed n'existe (aucune clé prisma.seed, aucun prisma/seed.ts) ; les 42 migrations créent uniquement la structure (tables, index, contraintes uniques). Les données de test du développement vivaient dans .localpg (non versionné, non livré). Repartir de zéro plus tard : db:down → supprimez apps/api/.localpg/ → db:up → migrate deploy.

Section 7
Lancement du projet
Démarrer la base
pnpm api:db:up
Tout lancer (recommandé)
pnpm dev # turbo dev : API :4000 + Web :3000
Ou séparément (deux terminaux)
pnpm api:dev # terminal 1 — API :4000 pnpm --filter @cosmoz/web dev # terminal 2 — Web :3000
Ouvrir l'application
Web : http://localhost:3000 · API : http://localhost:4000 (préfixe /api/v1). Le premier next dev compile à la volée : laissez 10-30 s.
Section 8
Premier accès & création de compte
Ouvrez http://localhost:3000 — écran d'authentification (groupe de routes (auth)).
Route /register : email + mot de passe fort. Hachage Argon2id (paramètres OWASP), anti-énumération d'emails, rate limiting multi-couches.
Email de vérification : en local sans SMTP, le mailer journalise le lien dans la console API — copiez-le dans le navigateur.
Connectez-vous, puis activez la MFA (TOTP) dans les réglages sécurité (secrets chiffrés AES-GCM, codes de récupération hachés à usage unique).
La base est vide : créez d'abord vos comptes de trading (mock provider activé en dev ; OANDA/Deriv en opt-in avec vos clés API), puis alimentez les autres modules.

Section 11
Build de production local
pnpm build # turbo build : next build + nest build
  • NODE_ENV=production désactive mock trading provider et mock OCR — une vraie OCR_SERVICE_URL devient requise.
  • CORS_ORIGINS doit lister vos origines exactes (* rejeté).
  • Erreurs 5xx masquées côté client, aucun stack trace ne fuit ; headers de sécurité posés par le web (XFO, nosniff, referrer, CSP frame-ancestors).
  • TRUST_PROXY=true uniquement derrière un reverse proxy HTTPS de confiance.

Section 14
Sécurité & bonnes pratiques
  1. Secrets : régénérez les 4 clés si vous exposez l'app au-delà de localhost. Ils ne quittent jamais votre machine.
  2. Fichiers .env : exclus du dépôt et surveillés par la garde CI — ne forcez jamais git add -f apps/api/.env.
  3. Mots de passe : Argon2id côté serveur ; n'abaissez jamais les paramètres.
  4. MFA : activation recommandée dès le premier login.
  5. Providers réels (OANDA/Deriv) : opt-in explicite, clés chiffrées AES-256-GCM au repos, jamais retournées par l'API.
  6. Webhooks entrants : HMAC + fenêtre anti-replay intégrés.
  7. Mises à jour : pnpm audit --prod doit rester à 0 ; respectez les overrides de pnpm-workspace.yaml.
  8. Backups : pg_dump + copie de apps/api/.env hors machine — c'est votre seul état irremplaçable une fois vos données saisies.
